# src/ Agent Instructions

## config.py

- `Config` is a frozen (immutable) dataclass returned by `load_config()`. All fields use attribute access (`config.dry_run`). Mutations require `dataclasses.replace()` for tests or editing `config.yaml` for production. `load_config()` deep-copies `DEFAULTS` before merging user YAML, then converts list fields (`active_rules`, `preferred_hours`, `undesired_hours`) to tuples for hashability.
- **`_deep_merge` treats `None` as a legitimate overlay value**: An empty YAML field like `disliked:` (no value) becomes `None` and overwrites the default `[]`. Code guards (`locations = locations or []`) are the second line of defense when config drifts.

## calendar_client.py

- `_authed` is only set to True inside `authenticate()`. If auth raises `CalendarError`, `_authed` stays False and `get_weekly_hours()` returns 0.0 — weekly caps are bypassed, shifts flow through without protection.
- **Caching is inline in `CalendarClient`** (the standalone `EventStore` class was merged in and deleted): `_get_cached_events()` manages in-memory cache (`_cached_events`, `_cache_time`, `_cache_window_start/end`), file cache (JSON read/write with atomic rename), TTL expiry, and window-keyed invalidation. Lookup order: exact in-memory match → superset in-memory match via `_filter_by_window` → file cache → `_fetch_all_events`. `_invalidate()` deletes the cache file AND clears in-memory state.
- **`_parse_event_dt` is module-level**: Window filtering (`_filter_by_window`, `_overlaps`) needs to parse event datetimes without a CalendarClient instance. Extracted to a module-level function also used by the `compute_shift_context` helpers.
- **`_fetch_all_events` has a dry_run guard returning `[]`**: The guard lives inside the fetch method so every cache path sees empty results in dry_run mode. Previously dry_run was checked in individual CalendarClient methods.
- `CalendarClient.__init__` stores cache config (`cache_file`, TTL) and initializes empty in-memory cache state — no fetch happens at construction. All read methods (`get_events_between`, `get_weekly_hours`, `get_adjacent_events`, `check_conflict`) funnel through `_get_cached_events()`.
- `invalidate_cache()` delegates to `self._invalidate()`, which does `os.remove(self._cache_file)` plus an in-memory state clear. The in-memory clear is dead code in practice — the process exits immediately after.
- Test mocks that bypass `authenticate()` by assigning `_service` directly must also set `_authed = True`. `get_weekly_hours()` returns 0.0 when `not self._authed`, even with a fully mocked service.
- `ZoneInfo('America/Los_Angeles')` requires `tzdata` package on Windows — Python on Windows doesn't bundle IANA timezone data. Missing package causes `ZoneInfoNotFoundError: 'No time zone found with key America/Los_Angeles'`.
- Auth failure during refresh is silent: if `authenticate()` raises `CalendarError`, `get_weekly_hours()` returns 0.0 without fetching. Existing cache file survives untouched. `--refresh-cache` still prints "Calendar cache refreshed" and exits 0 — no error raised.
- **File-cache superset was removed** (superset match from `calendar_cache.json`): caused test contamination where a prior test's mock data loaded instead of the current test's mock. The superset check is in-memory only within a single process. File cache serves exact-window reuse across process restarts.
- **`check_conflict` now accepts `cc_only: bool = False`**: When `True`, it skips non-`[CC]` events and returns the first CC conflict. Only the `rule_calendar_conflict` path passes `True` (via `compute_shift_context`) — generic callers still see all events.
- **Lazy-load heavy Google imports inside `authenticate()`**: `google.oauth2.service_account` and `googleapiclient.discovery.build` were moved from module level into `authenticate()` body. Prevents `ImportError` on `import calendar_client` when `google-api-python-client` is missing. `HttpError` stays module-level — it's used in 3 methods and duplicating the import gains nothing. **CORRECTION: `from googleapiclient.errors import HttpError` at module level is NOT lightweight — importing ANY name from `googleapiclient.*` loads the full package tree (~870ms on Termux).**
- **LSP `| None` type errors can be pre-existing false positives**: Lines 73 and 104 return `self._cached_events` after `is not None` guards, but the LSP type checker reports `Type "List[Dict[str, Any]] | None" is not assignable`. These existed before any import changes; the LSP re-validated the file after edit and surfaced them. Code is correct at runtime — don't chase unless tests fail.
- **`add_shift_event` returns `"dry-run-event-id"` when `self._service` is None (auth failed or skipped)**: `_handle_confirmation` then skips the ✅ push in live mode and logs the fake id — the calendar event is never created and nothing records the skip. A silently-dead calendar looks exactly like success in the log (issue #48).

## parser.py + rules.py

- `parse_shift_text` returns `(ParsedOffer, list[str])` — a tuple of the immutable parser output and a separate list of parse error strings. The parser no longer mutates `decision_reasons`.
- `classify_incoming()` is the single classification entry point. The parser trusts the caller to pre-classify — it no longer runs its own internal classification (`_classify_non_offer_text` was deleted).
- Parse errors flow as an explicit `parse_errors` parameter through `RulesEngine.evaluate()` (`process_offer` passes them from `parse_with_fallback`), not filtered from `offer.decision_reasons` via a fragile `benign` set.
- `ParsedOffer` is the single canonical offer type — `ShiftOffer` no longer exists. `rules.evaluate()` returns `ScoredOffer(offer, score, decision, reasons, calendar_event_id)` — no mutation of the input offer. Score, decision, and reasons live on the returned `ScoredOffer`, not on the input.
- Both `ParsedOffer` (parser output) and `ScoredOffer` (rules output) are frozen dataclasses. Tests that need non-default field values must pass them at construction time, not mutate after. For example, overtime tests pass `shift_note="overtime eligible"` to `_make_offer()` instead of setting `offer.shift_note` after construction.

## responder.py

- `log_event()` writes JSON to structured log file; `_stderr()` writes to stderr. Not interchangeable. Exception branches in `_send_push` must include both.
- **`log_event` swallows ALL exceptions** (`except Exception: pass`): read-only path, disk full, bad perms → logging dies silently with no signal anywhere. Never treat "no log entry" as proof of "no run".
- ntfy action buttons use `"action": "http"` + URLs pointing to Tasker HTTP server. ntfy cannot invoke Android intents or Tasker tasks directly.
- `_send_push` errors silently invisible in JSON log if `log_event(...)` missing from except block — only goes to stderr.
- ntfy `priority` field must be integer (1-5), not string. Sending `"high"` returns 400 "invalid request: request body must be valid JSON" — that error is misleading; the JSON is valid, the field type is wrong.
- `_send_push` returns `bool` — `True` on success, `False` on failure.
- `termux-sms-send -s <slot> -n <number>` sends **FROM** that SIM slot's number **TO** the recipient. The `content://sms/sent` table stores the recipient as `address`, not the sender.
- `_send_push` accepts optional `message_id` — passes `X-Message` HTTP header so ntfy replaces previous notification with same ID in-place.
- `send_booking_push` replaces via `X-Message` only when the caller passes `message_id`. `_handle_confirmation` passes it (matching ⏳ key); `_handle_rejection` cannot (raw rejection text lacks data for `shift_key`).
- `send_booking_push` defensively handles empty `offer.title`, `start_time`, and `duration_hours` — rejection texts have no parsed fields. Falls back to `raw_text[:80]`, "Time unknown", "Address unknown".
- **`subprocess.run` in a daemon thread is unsafe for fire-and-forget SMS**: `run` blocks until the child exits; if the main thread exits first, the daemon thread dies before spawning `termux-sms-send`. `subprocess.Popen` spawns the child and returns immediately (<10 ms), making it safe for daemon-thread dispatch.
- **`Popen(..., stdin=subprocess.PIPE)` yields `Optional[IO]`**: `p.stdin` can theoretically be `None`. Write the SMS body only after a `p.stdin is not None` guard.

## parser.py

- `load_sample_shifts()` is the canonical sample loader — imported by both `test_parser.py` and `main.py`. Do not re-implement the `## heading` + accumulator pattern.
- **`ParsedOffer` sentinel for failed parses**: `start_time` and `end_time` default to `datetime(1970, 1, 1)` when the header can't be parsed. This sentinel is never checked by downstream code — `parse_with_fallback` uses the presence of `_EMPTY` or `_NO_HEADER` in the errors list to detect header failure.
- **`_EMPTY` and `_NO_HEADER` error taxonomy**: Module-level string constants used as error keys. `parse_with_fallback` checks for these to decide whether to try custom parsers. If neither is present, the main parser succeeded.
- Both `parse_shift_text()` and `parse_confirmation()` now return `ParsedOffer` — no type inconsistency. Downstream code receives `ParsedOffer` from either path.
- Building Lockout phone numbers in shift notes appear in two formats: `Contact @503-xxx-xxxx` (matches `LOCKOUT_CONTACT_RE`) and bare without keyword (e.g., `Unit112 5035550142`). The `_extract_contact` fallback regex must handle both — the test sample "c" only covers the `Contact @` variant.
- `_resolve_building()` splits brackets on `" - "` and matches the left segment. Entries like `"River Haven - CBA"` in `_bracket_to_building` are now redundant — new buildings with role suffixes only need the base name key.
- `HEADER_LOOSE_RE` is tried only after `HEADER_RE` fails. Adding sloppy patterns to the loose regex is safe — it can't cause false positives on text the strict pattern already matches.
- `classify_incoming()` runs before any parsing — routes confirmation/rejection texts away from `_process_shift`. The default return is `"offer"` (everything that's not a confirmation, rejection, or empty string).
- `parse_confirmation()` uses `CONFIRMATION_HEADER_RE` which matches the `"Congratulations! You are now booked..."` prefix. Inner structure (bracket, date, time) reuses `_resolve_building()` and date helpers from offer parsing.
- `classify_incoming()` checks rejection BEFORE confirmation. Order: garbage → rejection → confirmation → offer. Swapping could misclassify if patterns ever overlap (currently mutually exclusive).
- Module-level state containers that are never read or written (e.g. `_PENDING_SHIFTS`) are dead code creating false expectations about cross-process persistence. Prefer stateless handlers.

## main.py

- `pipeline.process_offer()` is the thin router — `classify_incoming(text)` dispatches to `_handle_confirmation`, `_handle_rejection`, or `_process_shift`. All entry points (`--text`, `--sample`, stdin) reach it via `main()` — no entry point calls `_process_shift` directly.
- Calendar events are deferred: `_execute_accept` only sends SMS + pending push (⏳). Calendar event creation happens later in `_handle_confirmation` when the shortcode confirms booking.
- Push notifications link via `X-Message` ntfy header — `offer.shift_key` produces a deterministic MD5 hash from `building|title|start_time`. `_execute_accept` and `_handle_confirmation` compute the same key to replace ⏳ with ✅.
- `_handle_rejection` sends a new ❌ push, not a replacement: rejection SMS arrives in a separate process invocation (Tasker wrapper spawns `python src/main.py` per SMS), so no in-memory state survives. The rejection text also lacks `building|title|time`, making `shift_key` impossible.
- `_execute_accept` fires `send_accept` via `threading.Thread(daemon=True)` — script can exit before SMS completes. Workaround for 6-10s `termux-sms-send` latency. After switching to `subprocess.Popen` (returns immediately), the thread was changed to `daemon=False` so the main thread waits the <10 ms needed for the child to spawn before exiting.
- `_handle_confirmation` only sends push in dry-run mode or when calendar event creation succeeds. If `add_shift_event` returns None in live mode, the booking push is silently skipped.
- `_handle_confirmation` no longer mutates `offer.calendar_event_id` — `ParsedOffer` is frozen. The ⏳→✅ push link travels through `send_booking_push`'s `message_id` parameter (set to `offer.shift_key`), not through the offer object.
- Different flow paths receive different types: `_execute_accept` gets `ScoredOffer` (has score/decision/reasons). `_handle_confirmation` and `_handle_reply` get `ParsedOffer` (parser output only). `--reply-offer-json` reconstructs `ParsedOffer` from JSON.
- `ShiftAutomator` class is deleted — all logic lives in `pipeline.py` (`process_offer`, `_execute_accept`, `_handle_confirmation`, `_handle_rejection`) and module-level helpers in `main.py`. The `[ShiftAutomator]` prefix in print messages is cosmetic, not a class reference.
- `--refresh-cache` happens during `_build_calendar()` — constructs and authenticates `CalendarClient` (no event fetch). The early return in `_handle_cli_actions` skips all subsequent flags.
- **Weekly hours are computed for the shift's own week**: `compute_shift_context()` derives `week_start` from the shift's `start_time`, so an earlier-week shift is no longer capped against the current week's busy schedule. The rule reads `context.weekly_hours`; the `_compute_weekly_hours` helper and `weekly_hours` parameter have been removed.
- **`_resolve_input` returns `str`, NOT `Tuple[str, bool]`**: After the refactor that removed the `done` flag, calling `_resolve_input(args)[0]` extracts the first CHARACTER, not the full text. The `_handle_cli_actions` helper does `return _resolve_input(args)` — no indexing.
- **`_format_result` checks `offer.start_time.year > 2000` for sentinel**: Failed parses have sentinel date `datetime(1970, 1, 1)`. The presenter outputs ISO datetime when `year > 2000` and `null` otherwise.
- **`from __future__ import annotations` makes type annotations lazy (string-evaluated)**: Use this at the top of `main.py` so that type annotations referencing names not yet in module scope (e.g. `Config`, `CalendarClient`) don't cause runtime `NameError`. The annotations are stored as strings and never evaluated at import time—only evaluated by type checkers at dev time.
- **Avoid `globals()` injection for lazy imports — pass dependencies as explicit parameters to helper functions**: `globals()['Name'] = _m.Name` works but creates implicit coupling (module-level helpers reference names that aren't visibly in scope). Prefer: `_check_tasker(url, http)` instead of relying on `requests` in globals; `_build_calendar(config, CC, CE)` instead of `CalendarClient`/`CalendarError` in globals; `_build_responder(config, SMS, create)` instead of `SMSConfig`/`create_responder` in globals. Call these from `main()` using module aliases like `_cfg.load_config()` — dot notation preserves context per the style guide.
- **LSP reports false "X is not defined" errors after lazy imports**: When `Config`, `CalendarClient`, `Responder`, `SMSConfig`, `CalendarError`, `create_responder` are removed from module-level scope, the LSP still tries to resolve them in type annotations despite `from __future__ import annotations` making them lazy. These are false positives — runtime is unaffected. Ignore unless tests break.
- **Lazy imports target heaviest transitive chains**: `config` → yaml (~100ms); `calendar_client` → googleapiclient (~870ms); `requests` → urllib3 + charset_normalizer (~1.7s). Profile with `python -X importtime`.
- **`init_logging()` runs at line 270 — after all lazy imports, config load, and calendar build**: any crash before that line (`ModuleNotFoundError`, config error, auth hang) leaves zero trace in `shift_automator_log.json`. A missing log entry does NOT mean the pipeline didn't run — cross-reference Tasker runlog `RunShiftBot` executions against the log to detect silent crashes (issue #48: phone env broken 24h+, claims still fired natively).
- **Claim-first single-claimer contract (final state)**: Tasker's native Send SMS (task42 act2) is the ONLY claimer. Immediately after it fires, task42 act21 writes `/sdcard/Tasker/shift_claim_sent.txt` (`claim_code epoch`). Python (`main.py`) NEVER sends a claim SMS — the deleted `_fire_claim_sms` / `_quick_veto` / `_extract_claim_code` (main.py) / `SMS_TARGET` fast path and the `SHIFT_AUTOMATOR_FAST_CLAIM` env var are gone. `_execute_accept` reads the marker via `_native_claim_already_sent()` for the accept-skip log entry and decline cancel-warnings; the `--send-accept` CLI flag is the only remaining SMS escape hatch.
- **Sleep-window gating lives in Tasker task42 act1 + the rules engine only**: The old `h >= 22 or h < 6` `_quick_veto` and the `data/shift-bot` BLC grep guard were native-claim pre-gates and are removed. Tasker act1 (op 3 glob NOT-match for `*Building Lunch Coverage*`, op 5 regex NOT-match for the sleep-start regex) plus the full rules engine (`rule_wakefulness_gate`, `rule_time_of_day` with `veto_undesired_hours`) are the two remaining layers — when the sleep window changes, update task42's act1 regex AND those rules, then re-deploy the XML.
- **`_check_tasker()` blocks for full 3s when Tasker HTTP Server is unreachable**: Called on every pipeline run. When Termux is backgrounded, `requests.get(url, timeout=3)` blocks the entire run for the full timeout. The native claim already fired before Python starts, so this is latency, not correctness. (This block was previously hidden behind the fast-path SMS; the single-claimer design keeps it visible but harmless.)
- **The deleted fast-path is NOT coming back**: re-adding an env var or SMS thread in `main()`/`_execute_accept` recreates the double-claim race that this repo shipped twice (issue #43 + the 2026-08-05 runlog: "Congratulations" :09 then "Sorry, already taken" :11). Any new claim mechanism must be written in Tasker and record the marker file.

## pipeline.py

- **`process_offer(text, config, calendar, responder)` is the entry point**. The `calendar` dependency feeds `compute_shift_context()` once per evaluation; rules read the shared `ShiftContext` (`context.weekly_hours`, `context.day_hours`, ...) instead of calling the calendar directly.
- **`shift_key` is now `ParsedOffer.shift_key` property** — deduplicates the format from two callers (`_execute_accept` and `_handle_confirmation`). The property uses `start_time.year > 2000` guard before appending the date to the hash input, so unscheduled offers still produce a non-empty key.
- **PipelineResult type was unchecked by Python**: `_handle_confirmation` passed `parsed=False` instead of `parsed=None` on parse failure — `PipelineResult` is not frozen, no type check at runtime, `False` stored as field value. Downstream `_format_result` uses `if result.parsed` short-circuit so `result.parsed.title` was never evaluated on the falsy `False`. Fixed by using `parsed=None` (correct default).
- **`_handle_confirmation` returns `PipelineResult(kind="confirmation", error="...")`** with `parsed=None` when `parse_confirmation()` fails — the caller must check `result.parsed` before accessing title/building.
- **Action string order is part of the test contract**: `test_presenter.py` asserts exact `actions` list contents and order from `PipelineResult`. Reordering operations in `_execute_accept` / `_execute_decline` must also reorder the corresponding dry-run action strings. Mismatched order breaks tests silently.
- **`_execute_accept` runs three synchronous steps in order** (single-claimer, no threads): 1) pending push, 2) `_native_claim_already_sent(code)` → SKIPPED, 3) else WARNING "no claim marker ... — Tasker native claim may have failed". It NEVER calls `responder.send_accept` — the native SMS thread and daemon-thread lifecycle contract are gone (if the main thread dies mid-run, the only loss is the log/push, never a claim).
- **`_execute_decline` flags cancel-warnings off the marker, not an env var**: `claimed = _native_claim_already_sent(code)`; when claimed it appends a WARNING "call dispatch to cancel" and passes `claimed=True` to `send_decline_push` (which adds the "⚠️ ALREADY CLAIMED" body line). The `SHIFT_AUTOMATOR_FAST_CLAIM` env var no longer exists.

## rules.py

- `RuleFn` type: `(ParsedOffer, Config, Optional[ShiftContext], Optional[list[str]])`. All rules take a 4th `parse_errors=None` parameter even though only `rule_parsing_quality` used it (since removed). `evaluate()` returns `ScoredOffer` — callers get `scored.score`, `scored.reasons`, `scored.decision`. Rules no longer mutate the input offer.
- `VETO_DECLINE` overrides scoring entirely — if any rule returns VETO_DECLINE, the shift is auto-declined regardless of accumulated score.
- `RulesEngine.__init__(config, calendar=None)` stores the explicit `calendar` param. `evaluate()` calls `compute_shift_context(offer, calendar)` once and passes the resulting `ShiftContext` to each rule. Rules that need calendar data (`calendar_conflict`, `day_hours_cap`, `post_cap_break`, `rest_gap_sleep`, `weekly_hours_cap`) read precomputed fields off the context.
- **`FLAG` action shows reasons without adding score**: Unlike `SCORE` (adds to total) or `VETO_DECLINE` (block), `FLAG` only appends a reason string to `decision_reasons` with no score impact. Used by `rule_weekly_hours_cap` when skipped (sentinel date or missing calendar) and `rule_calendar_conflict` when no calendar client available.
- **Binary threshold comparison is strict greater-than**: `evaluate()` uses `score > auto_decline_threshold` — not `>=`. A score of exactly -5.0 with threshold -5.0 results in AUTO_DECLINE. Tests for boundary conditions must use -4.9 and -5.0, not -5.0 vs -5.1.
- `veto_undesired_hours: true` makes `undesired_time_penalty` dead config — `rule_time_of_day` returns `VETO_DECLINE` before the penalty is applied.
- **Config keys for rules absent from `active_rules` are dead weight**: When removing a rule from `active_rules`, remove its config entries in the same commit. A config key without the corresponding rule name in `active_rules` has no effect but reads as active.
- **`context.adjacent_events` contains ALL calendar events** (unfiltered): `rule_rest_gap_sleep` must filter by `[CC]` prefix itself (via `_filter_cc_events`) — the context builder does not know which events are work shifts. This differs from `context.weekly_hours`, which `_sum_cc_hours` computes from `[CC]` events only.
- **`rule_time_of_day` skips malformed `undesired_hours` entries**: Entries that don't unpack to exactly 2 values are silently skipped, preventing crashes from config typos like `[24]`.
- **`rule_rest_gap_sleep` uses `rest_gap_sleep_hours` for both lookback/lookahead AND minimum gap**: Changing this key affects both the search radius and the threshold. The old `rule_rest_gap` used `strict_hours` (8.0) for the window and a separate `relaxed_hours` (1.0) for the relaxed threshold.
- **`rule_wakefulness_gate` reads `datetime.now()` at evaluation time, not from the offer**: The offer's `start_time` determines if the shift starts in the sleep window; `datetime.now()` determines if it's currently too early to accept. Tests must patch `rules.datetime` because `rules.py` imports `datetime` at module level.
- **`rule_day_hours_cap` and `rule_post_cap_break` are VETO rules that read the shared `ShiftContext`**: `day_hours_cap` reads `context.day_hours` (midnight-to-midnight of the offer's date); `post_cap_break` reads `context.prev_day_hours` / `context.prev_day_last_end` (the previous day). Both windows are computed once in `compute_shift_context`.
- **Stripping imports may reveal dead code that should also go**: Removing `import yaml` from `rules.py` broke `from_yaml()` — the sole consumer. `from_yaml()` was already dead (never called; `config.py` parses YAML). When removing imports, check if dependent code is also dead rather than re-adding the import.
